# Аудит разметки атак: отчёт

Задание: `docs/LABEL_AUDIT.md`. Проверка проведена по коду проекта (коммит `1f6d374`), по коду LID-DS (`dataloader/*_2021.py`, `lid_ds/core/*`, `algorithms/performance_measurement.py`, ветка master) и на синтетическом сценарии в формате LID-DS 2021. Реальные данные не открывались. Код проекта не менялся.

Синтетика (во временной папке, не коммитится): архив `SYN.zip` из 22 записей. В каждой строке `.sc` в параметрах стоит метка `i=<номер строки>`, чтобы отследить, какая строка куда попала. Время начинается с `1631609100123456789` нс, шаг 1 мс (в записях для проверки точности шаг 1 мкс). Конвертер запускался без изменений: `python experiments/lid_ds/convert.py SYN.zip --out ...`.

## Краткий итог

1. Гипотеза о «хвосте» подтверждается кодом. Атакой помечается всё от первого шага эксплойта до конца записи, а метка окна равна имени папки, без исключений. В LID-DS нормальные клиенты работают всё время записи, эксплойт выполняется отдельными командами, и поля «конец атаки» в метаданных нет. Значит, нормальный трафик после эксплойта неизбежно размечен как атака. Какая это доля окон, зависит от длины хвоста, а её можно измерить только на данных (раздел 4, проверка D1).
2. Ошибок в преобразовании времени нет. Обе стороны используют unix epoch без часовых поясов, погрешность float64 не больше ±240 нс, то есть граница сдвигается не больше чем на одну строку.
3. Прогрева в `.sc` по коду LID-DS быть не должно: sysdig стартует после `warmup_end`. Проверить это на данных дёшево (D4).
4. Найдены мелкие дефекты конвертера, которые на метки почти не влияют: строки с немонотонным временем после эксплойта выпадают молча; JSON с одинарными кавычками приводит к потере записи; `--balance-test` может заметно промахнуться мимо цели. Короткие атакующие сегменты (меньше 65 строк) выпадают из оценки целиком.

## 1. Поток меток

1. **zip LID-DS → список записей.** `_scan_archive` / `_scan_dir` (`experiments/lid_ds/convert.py:87-121`). Для каждой записи запоминаются сплит (`training` / `validation` / `test`) и имя папки (`folder`: `normal` или `normal_and_attack`). Отбрасываются `__MACOSX` и `._*`.
2. **Метаданные → время эксплойта.** `read_metadata` (`convert.py:66`), `exploit_start_ns` (`convert.py:72-79`): `min(time.exploit[].absolute) * 1e9`, или `None`.
3. **Маршрутизация записи** (`convert_recording`, `convert.py:135-149`):
   - эксплойт в training/validation → пропуск (`skipped: exploit outside test split`);
   - `exploit: true` без времени → пропуск;
   - `test/normal_and_attack` без эксплойта → пропуск;
   - без эксплойта → `training/`, `validation/` или `test/normal/` целиком;
   - с эксплойтом → `test/abnormal/<имя>.sc`.
4. **Построчный фильтр** (`convert.py:159-172`):
   - `convert_line` (`convert.py:51-63`) отбрасывает строки, в которых не больше 6 полей или время не число, и считает их в `bad_lines`;
   - в атакующей записи строка с `ts_ns < attack_ns` пропускается (`convert.py:167-170`). Это сравнение по каждой строке, а не разрез по позиции.
   - пустой выход удаляется, статус `empty` (`convert.py:178-184`).
5. **Баланс** (`balance_test`, `convert.py:188-221`, по флагу) удаляет целые файлы из `test/normal`.
6. **Чтение.** `test_recording_files` (`syscall_hids/data/layout.py:62-75`): normal и abnormal по папкам. `read_recording` (`syscall_hids/data/parsing.py:43-51`) отбрасывает `switch` и строки короче 4 полей. Время переводится в float-секунды (`parsing.py:35`), но дальше не используется.
7. **Окна.** `make_sequences` (`syscall_hids/data/sequences.py:37-58`). Для test шаг равен `seq_len`: `tools/train.py:151`, `cli/eval_recordings.py:106-107`, `cli/calibrate.py:180`. Записи короче `seq_len+1` строки пропускаются (`sequences.py:117`, `calibrate.py:144`).
8. **Метка окна.** `np.full(len(X), is_attack)` по папке (`sequences.py:125`). В `hids-calibrate` метка берётся из `rec_is_attack[rec_idx]` (`calibrate.py:185,198`).
9. **Метрики.** Оконные. В `hids-train` / `hids-eval` это `classification_report` и ROC-AUC (`tools/evaluation.py:103-126`). В `hids-calibrate` записи делятся на calib и holdout со стратификацией (`tools/calibration.py:14-31`, `calibrate.py:398-400`), считаются оконные TP/FP (`calibration.py:41-48`), бутстрэп идёт по записям.

## 2. Ответы на вопросы

### В1. Поле времени, несколько эксплойтов, крайние случаи

Время берётся из `time.exploit[].absolute`, используется минимум (`convert.py:76-79`). Официальная оценка LID-DS берёт `time.exploit[0].absolute` (`algorithms/ids.py:173`, `performance_measurement.py`, `new_recording`). Шаги дописываются по порядку выполнения (`lid_ds/core/objects/attacker.py`, `execute_exploit_at_time`), поэтому `[0]` и `min` совпадают, пока постобработка не сдвинула время шагов. `min` надёжнее.

Откуда несколько элементов: каждый элемент `exploit[]` — шаг цепочки эксплойта (`ChainImage.commands`) со своим `name`. После записи `optimize_attack_time` может уточнить время шага по пакету tcpdump или событию sysdig (поле `source`: `CONTROL_SCRIPT` / `TCPDUMP` / `SYSDIG`).

Синтетика (S1):

| Вход | Результат |
|---|---|
| `a_multi`: 100 строк, `exploit[]` = строки 70, 40, 55 (не по порядку) | `test/abnormal/a_multi.sc`: строки 40–99 (60 строк), граница = min |
| `a_empty`: `exploit: true`, `exploit: []` | `skipped: exploit=true without exploit time` |
| `a_noabs`: `exploit: true`, элемент без `absolute` | то же |
| `a_falseflag` в `normal_and_attack`: `exploit: false`, список не пуст | `skipped: no exploit in test/normal_and_attack` |
| `n_falseflag` в `test/normal`: `exploit: false`, список не пуст | целиком в `test/normal` (флаг `exploit` главнее списка) |
| `a_late`: эксплойт через 450 мс после последней строки | статус `empty`, файла нет, в test не попадает |
| `tr_exploit`: эксплойт в training | `skipped: exploit outside test split` |

Все пропуски видны только в `manifest.json`, предупреждений в консоли нет: выводится лишь сводный счётчик статусов (`convert.py:315-318`).

### В2. Единицы, точность, точка отсчёта

- `.sc`: целые наносекунды unix (`Syscall2021.timestamp_unix_in_ns`). Метаданные: float-секунды unix. Их пишет `Collector._calculate_time_value` через `time.time()` (`lid_ds/core/collector/collector.py:24-41`) или берёт время пакета tcpdump / события sysdig. Всё это epoch на одном хосте, часовых поясов нигде нет.
- Преобразование `int(min(times) * 1e9)` (`convert.py:79`) верное. Шаг float64 около 1.63e9 с равен 238 нс. На 200 000 случайных отметок 2021–2023 годов ошибка `int(x*1e9) − t` лежит в пределах [−128, +128] нс, а если источник имеет микросекундное разрешение — в [−240, +240] нс.
- Синтетика S2 (строки через 1 мкс, эксплойт ровно на строке 30, на 1 нс позже и на 100 нс раньше): во всех трёх случаях граница пришлась на строку 30. В `a_short9` (строки через 1 мс, эксплойт ровно на строке 91) float округлился вверх на 43 нс, и строка 91 ушла в отброшенную часть (сегмент 8 строк вместо 9). Сдвиг не больше одной строки и только если между syscall'ами меньше ~250 нс. Практического значения не имеет.
- Поля отсчёта: `container_ready.absolute`, `warmup_end.absolute`, а у каждого шага эксплойта ещё `relative = absolute − warmup_end.absolute` (`collector.py:38-41`). `absolute` уже абсолютное, поэтому `warmup_end` для перевода времени не нужен, и использовать `absolute` правильно. В коде официальной оценки рядом с этим местом стоит `# TODO: fix the timestamps` (`performance_measurement.py`, `new_recording`). Что именно имелось в виду, из кода не видно. Систематический сдвиг можно проверить на данных: строки атакующего процесса или пакеты должны начинаться сразу после `exploit_start_ns` (D1, гистограмма около нуля).

### В3. Какой отрезок становится атакой

`[min(exploit.absolute), последняя строка записи]`. Верхней границы нет (`convert.py:167-168`). В метаданных LID-DS 2021 есть только `container_ready`, `warmup_end`, `exploit[]` (`absolute`, `relative`, `name`, `source`), `recording_time` (`recording_2021.py`, `metadata()`). Конца атаки и длительности нет. Шаги (`exploit[]`) мы используем только через `min`. Время последнего шага, которое могло бы дать нижнюю оценку конца активной фазы, не сохраняется даже в `manifest.json`.

Длину хвоста косвенно задаёт режим записи LID-DS (`lid_ds/core/scenario.py`, `_recording`). При `recording_time=-1` запись останавливается через случайные 5–15 с после выхода контейнера атакующего. Иначе запись длится фиксированные `recording_time` секунд, а эксплойт стартует через `exploit_start_time` после прогрева, и хвост может быть длинным. Какой режим использован в PHP_CWE-434, по коду не определить. Это даст D1: распределение `t_последней_строки − t_эксплойта`. Нормальные клиенты (`ScenarioNormal.start_simulation`) запускаются до записи и работают всю запись, в том числе после эксплойта.

### В4. Часть атакующей записи до эксплойта

Отбрасывается (`convert.py:170`): она не попадает ни в `test/normal`, ни куда-либо ещё. В `manifest.json` число отброшенных строк не пишется. Синтетика S3 (`a_multi`): строк `am0`–`am39` нет ни в одном выходном файле. С README (`experiments/lid_ds/README.MD`, таблица и раздел «Ограничения») совпадает.

Следствие: FPR меряется только на «чистых» нормальных записях. Нормальный трафик в записях с атакой до эксплойта в оценке не участвует, хотя в реальной работе детектор увидит именно его.

### В5. `--balance-test`

- Удаляются **целые файлы** и **только из `test/normal`**. Abnormal, training и validation не трогаются, строки внутри не обрезаются (`convert.py:197-212`). Цель — сумма `lines.attack`. Эти счётчики включают строки `switch`, которые потом выбрасывает `read_recording`, так что баланс считается в «сырых» строках.
- Отбор жадный: файлы перемешиваются с seed, файл остаётся, если `kept + n/2 <= target`.
- Окна сразу после эксплойта удалить **не может**: abnormal не трогается.
- Детерминизм: результат зависит только от seed и порядка записей (сортировка по имени в архиве, `convert.py:109`). `--rebalance` по `manifest.json` даёт тот же набор.

Синтетика S4 (6 нормальных файлов: 30, 80, 120, 200, 30, 40 строк; abnormal 8 файлов, 209 строк):

| Запуск | Оставлено в test/normal | Строк (цель 209) | Abnormal |
|---|---|---|---|
| seed 0 | n2, n3, n_falseflag | 230 | побайтно без изменений |
| seed 0 повторно | то же | 230 | без изменений |
| seed 1 | n1, n3, n_falseflag, n_warm | 220 | без изменений |
| seed 7 | n1, n4, n_falseflag, n_warm | 300 (+44%) | без изменений |
| `--rebalance --seed 0` по манифесту | n2, n3, n_falseflag | 230 | — |
| повторный `--rebalance` | отказ, код 1 | — | — |

Оставленные нормальные файлы и train/val побайтно совпадают с конвертацией без баланса. Если файлы крупные относительно цели, промах может быть большим (seed 7). Это меняет долю атак среди окон, то есть precision, но не метки.

### В6. Прогрев

Конвертер `container_ready` / `warmup_end` не читает, и строки до `warmup_end` проходят без изменений в training, validation и test/normal. Синтетика S7: `tr_warm` и `n_warm` с `warmup_end` на строках 20 и 15 сконвертированы целиком (`trw0`–`trw49`, `nw0`–`nw39`).

Однако по коду LID-DS прогрева в `.sc` быть не должно. Порядок в `Scenario.__call__`: `set_container_ready()`, затем `_warmup()` (`sleep(warmup_time)`, `set_warmup_end()`, запуск нормальных клиентов и таймера эксплойта), и только потом `_recording()` запускает sysdig. Поэтому `t_первой_строки ≥ warmup_end` в каждой записи. Риск вероятен в другом месте: в начале любой записи есть «эффект старта» (подключение sysdig, первый всплеск клиентов). Он присутствует и в train, но занимает там малую долю окон. Объяснит ли он нормальные окна с самыми высокими оценками, покажет D3.

### В7. От файла до окна

- **Метка без исключений.** Каждое окно abnormal-файла получает `True` (`sequences.py:125`; `calibrate.py:185,198`). Синтетика S5a (`seq_len=8`, шаг 8): 89 окон, из них 26 атакующих = сумма окон шести допущенных abnormal-файлов. Ни одно окно не помечено иначе, чем его папка.
- **Короткие записи.** Нужно `seq_len+1` строк **после** удаления `switch` (`sequences.py:117`, `calibrate.py:144`). Сейчас `seq_len=64` (`configs/php_cwe_434.yaml`), то есть запись выпадает целиком, если в сегменте меньше 65 строк. Синтетика S5a: `a_short8` и `a_short9` (по 8 строк при пороге 9) дали 0 окон и исчезли из test без сообщения. Что это значит в секундах, зависит от темпа syscall'ов. При сотнях-тысячах syscall/с у веб-сервера 65 строк — это доли секунды, то есть выпадают только эксплойты в самом конце записи. Сколько их, покажет D2. Влияние на метрики: такие записи исчезают из числителя и знаменателя оконного recall и из числа записей в `hids-calibrate` (calib/holdout делятся без них). Recall на уровне записи по сравнению с LID-DS (`detection_rate`) завышается: самые трудные случаи (почти нет атакующих строк) в знаменатель не попадают.
- **Хвостовое окно.** Если `(n − 1)` не делится на `seq_len`, добавляется окно, прижатое к концу (`sequences.py:44-47`). Для шага `seq_len` соседние обычные окна делят ровно одну строку (цель последнего шага одного окна — первый вход следующего), а оценённые шаги не повторяются. Хвостовое окно оценивает заново `seq_len − ((n−1) mod seq_len)` шагов. Синтетика S5b (`seq_len=8`, шаг 8): при n=18 старты 0, 8, 9 и 7 шагов оценены дважды; n=20 → 0, 8, 11 и 5; n=30 → 0, 8, 16, 21 и 3; n=17 → 0, 8 без повторов. Первая строка записи никогда не бывает целью. Итог: не больше одного частично повторного окна на запись. Для коротких сегментов (65–128 строк) это до ~50% окон записи, что даёт таким записям лишний вес в оконных метриках. Для длинных эффект пренебрежим.

### В8. Отбрасывание строк

Фильтры одинаковы для normal и abnormal, и по самой метке асимметрии в коде нет:

- конвертер: не больше 6 полей или нечисловое время → `bad_lines` (`convert.py:53-59`). Счётчик `bad_lines` в манифесте считается по всей записи, включая отброшенную часть до эксплойта;
- `read_recording`: `switch` и строки короче 4 полей (`parsing.py:17,49`).

Синтетика S6 (`a_junk`, 6 мусорных строк после эксплойта): конвертер отбросил 3 (`garbage`, 4 поля, нечисловое время), записал 23. `read_recording` убрал ещё 2 `switch`, осталось 21. Строка без параметров (7 полей) сохранена с `arg_count=0`.

Найдены две асимметрии, которые проявляются **только в атакующих записях**:

- **Немонотонное время.** Сравнение `ts_ns >= attack_ns` идёт по каждой строке, а не разрезом по позиции. Синтетика `a_nonmono`: две строки со временем раньше эксплойта, вставленные после него, молча выброшены (`late_a`, `late_b` отсутствуют, `bad_lines=0`). Если sysdig пишет буферы CPU не строго по времени, в начале сегмента появятся «дыры». Они создают искусственные переходы, повышают NLL и **завышают** recall первых окон. В нормальных записях такого фильтра нет.
- **Доля `switch`.** Если в атакующих сегментах `switch` встречается чаще (нагрузка на CPU), эффективная длина сегмента меньше той, что видна в манифесте. На метки это не влияет, влияет на порог в 65 строк и на баланс. Проверка: D2.

Ещё две мелочи. Имя процесса с пробелом сдвинет колонки и в `convert_line`, и в `parse_log_line`; признак сдвига — направление, отличное от `>` и `<`. JSON с одинарными кавычками: официальный `Recording2021.metadata()` делает `replace("'", '"')`, а конвертер нет. Синтетика `a_squote` дала статус `error: JSONDecodeError`, запись потеряна. Но `DataLoader2021.collect_metadata` тоже читает JSON без замены, так что в реальном датасете такие файлы маловероятны. Проверка: статусы `error:` в манифесте (D5).

### В9. Время окон

Сейчас в конвейере время окон не сохраняется. `ParsedLine.timestamp` (`parsing.py:7,35`) есть, но `encode_recording` / `make_sequences` его не передают. Функции вида `make_sequences_with_time` нет нигде (`syscall_hids`, `experiments`, `tests`). Время окна строит только `detect_live.encode_tail` (`cli/detect_live.py:30-41`), и это realtime, к test отношения не имеет. Время эксплойта хранится в `manifest.json` (`exploit_start_ns`), а сам abnormal-файл уже обрезан, так что время от эксплойта = время строки − `exploit_start_ns`.

Минимально нужно: для каждого окна test знать индекс записи (в кеше уже есть `test_rec_idx`), индекс старта окна и время его последней целевой строки. Плюс соответствие «файл → `exploit_start_ns`» из манифеста.

| Вариант | Плюсы | Минусы |
|---|---|---|
| Побочный массив `test_win_t_end` в кеше `hids-calibrate` | время считается в том же проходе, расхождение исключено | меняется формат кеша (`CACHE_VERSION`), правка ядра ради анализа, повторный проход модели по всем данным |
| Отдельный скрипт по готовому кешу и `calibration.json` | ядро не трогается, модель не нужна, пересчёт только по `read_recording` | логика стартов окон дублируется; нужна проверка «число окон на запись = числу в кеше» (`np.bincount(test_rec_idx)`) |
| Общая функция `window_starts(n, seq_len, step)`, вынесенная из `make_sequences` | убирает дублирование для скрипта | малая, но правка ядра; нужен тест на совпадение с `make_sequences` |

Рекомендация: отдельный скрипт, дублирование закрыть сверкой числа окон. Вынести `window_starts` — потом и только с твоего согласия.

## 4. План проверки на данных

Всё ниже читает только уже сконвертированный `DATASET_LIDDS/PHP_CWE-434`, `manifest.json` и результаты `hids-calibrate`. Модель повторно не нужна. Предлагаю один отдельный скрипт `experiments/lid_ds/label_audit.py` (stdlib + numpy, читает строки через `read_recording`) с подкомандами ниже. Его пишем после того, как ты прочтёшь отчёт.

Входы: `{work_dir}/calibration/PHP_CWE-434/cache_PHP_CWE-434.npz` (`test_nll`, `test_rec_idx`, `test_files`, `test_rec_is_attack`), `calibration.json` (`selected.q`, `selected.threshold`, `split.holdout`, `windows.seq_len`), `DATASET_LIDDS/PHP_CWE-434/manifest.json`.

**D1. Recall по времени от эксплойта.**
1. Для каждого abnormal-файла из holdout: `read_recording` → времена строк. Старты окон пересчитываются как в `make_sequences` (шаг `seq_len`, хвост прижат). Проверка: число окон = `bincount(test_rec_idx)[r]`.
2. Для окна `dt = t[start+seq_len] − exploit_start_ns/1e9` (время последней целевой строки, то есть момент, когда оценка доступна).
3. Оценка окна = `aggregate(test_nll[rows], selected.q)`, тревога = `> selected.threshold`.
4. Таблица по интервалам 0–5 / 5–15 / 15–60 / >60 с: число окон, recall, медиана оценки. Отдельно гистограмма `dt` для всех окон и для пропущенных (FN).
5. На уровне записи: длина хвоста `t_последней − t_эксплойта` (распределение) и время до первой тревоги.

Ожидание при верной гипотезе R1: recall высокий в 0–5 с и резко падает дальше, FN сосредоточены при больших `dt`.
Запуск: `python experiments/lid_ds/label_audit.py recall-by-time --calib-dir runs/.../calibration/PHP_CWE-434 --dataset DATASET_LIDDS/PHP_CWE-434`.

**D2. Длины сегментов и выпавшие записи.**
- По манифесту: распределение `lines.attack` и число записей с `lines.attack < 65`.
- По файлам (точно, после удаления `switch`): `len(read_recording(f))` для каждого abnormal-файла, доля `switch` в abnormal против normal, число записей с `< seq_len+1`, число повторно оценённых шагов в хвостовом окне.
- Сверка: записей в `test/abnormal` против `len(test_files[test_rec_is_attack])` в кеше.

**D3. Где нормальные окна с самыми высокими оценками.**
Для нормальных окон holdout взять топ-N (например, все выше порога, при precision ≈ 0.67 на левом краю). Для каждого: файл, позиция `start/n`, `t_окна − t_первой_строки`. Гистограмма по позиции и время от начала записи (первые 5 с против остального). Если топ собран в начале записей — это R8; если в нескольких файлах — особые сессии.

**D4. Прогрев.** Для normal- и abnormal-записей test (и выборочно train) прочитать только `.json` из исходного zip (без `.sc`) и первую строку сконвертированного файла: `t_первой − warmup_end.absolute`. Ожидание: ≥ 0 у всех. Отрицательные значения означают прогрев в данных.

**D5. Целостность конвертации.** Из манифеста: счётчик статусов (`error:`, `empty`, `skipped`), `bad_lines`. По abnormal-файлам: число строк, где время меньше предыдущей строки (R5). По всем test-файлам: число строк с направлением не `>` / `<` (R12).

## 5. Предложения по исправлению

1. **Метрики на уровне записи** (рекомендую первым). Запись атаки обнаружена, если в ней есть хотя бы одна тревога; FP — тревога в нормальной записи; дополнительно время до первой тревоги. Это соответствует официальной метрике LID-DS (`detection_rate`, consecutive false alarms) и не зависит от длины хвоста. Объём: малый. Отдельный скрипт поверх кеша `hids-calibrate` (~80–100 строк), ядро не трогается. Позже можно добавить в `calibration.json` как ещё одну таблицу.
2. **Ограничение атакующего сегмента по времени.** В метаданных конца атаки нет. Варианты по убыванию обоснованности:
   - (a) горизонт H секунд от **последнего** шага `exploit[]`, H выбирается по D1;
   - (b) горизонт от первого шага;
   - (c) хвост после горизонта не удалять, а вынести в отдельную группу «не оценивать», чтобы не путать с нормой.

   Объём: малый в конвертере (флаг `--attack-horizon`, запись `exploit_times`, `last_ts`, `attack_horizon` в манифест). Вариант (c) требует третьей папки или маски, то есть правки `layout` / `sequences` — средний объём, только по согласованию. Делать после D1.
3. **Учёт прогрева.** По коду LID-DS не нужен. Если D4 найдёт строки до `warmup_end`, обрезать их в конвертере во всех сплитах. Объём: малый. Если подтвердится R8 (эффект старта, а не прогрев), обрезка не поможет: это вопрос данных train, и решение отдельное.
4. **Исправления конвертера** (малый объём, ядро не затрагивают):
   - писать в манифест `lines_before_exploit`, `first_ts`, `last_ts`, все времена `exploit[]` и число немонотонных строк, выброшенных фильтром;
   - решить, резать ли по первой позиции с `ts >= attack_ns`, а не по каждой строке (R5);
   - читать JSON с запасным `replace("'", '"')`, как в `Recording2021.metadata()` (R11);
   - печатать предупреждение при статусах `empty` / `error`;
   - при желании отдельной папкой сохранять часть атакующей записи до эксплойта, чтобы мерить FPR на ней (R9). Тогда её нельзя смешивать с `test/normal` без пометки.
